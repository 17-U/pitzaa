## Séquestre des paiements d'abonnement en plusieurs mois d'avance (décision prise)

- Pour un paiement de 3 ou 6 mois d'avance, j'ai choisi un séquestre unique de 48h sur la totalité du montant (un seul litige possible pour toute la période), plutôt qu'une libération progressive mois par mois à mesure que chaque période démarre. C'est plus simple et évite de retarder le paiement du propriétaire pour des mois à venir. Dites-moi si vous préférez une libération progressive.

## Litiges, arbitrage et score de confiance (Phase 5, décisions prises)

- **Qui peut trancher un litige, et quand** : j'ai autorisé un admin (`SUPER_ADMIN`/`MODERATOR`/`SUPPORT`) à trancher (`POST /disputes/:id/resolve`) un litige dès l'état `OPEN`, sans attendre que la partie mise en cause réponde ou que le délai de 48h expire (passage en `UNDER_ARBITRATION`). Rationnel : s'il y a déjà assez de preuves (captures jointes à l'ouverture), rien n'oblige à attendre. Dites-moi si vous préférez forcer le passage par `UNDER_ARBITRATION` avant toute résolution.
- **Valeur `AWAITING_RESPONSE` de l'enum `DisputeStatus`** : définie dans le schéma Prisma (Phase 1) mais volontairement inutilisée dans mon implémentation — un litige passe directement de `OPEN` à `UNDER_ARBITRATION` (sur réponse ou sur timeout), sans état intermédiaire distinct. Je n'ai pas identifié de différence fonctionnelle entre `OPEN` et `AWAITING_RESPONSE` dans le brief. Dites-moi si cette valeur doit porter un sens différent (p. ex. « vu par la contrepartie mais pas encore répondu »).
- **Barème du score de confiance** (`packages/shared/src/constants.ts` / `trust.ts`) — valeurs choisies par hypothèse raisonnable, à valider :
  - Avis 1-5 étoiles : impact `(note − 3) × 2`, donc de −4 (1★) à +4 (5★), neutre à 3★.
  - Litige perdu : −15 points pour la partie jugée fautive (aucun gain pour la partie qui a raison — le litige n'aurait simplement pas dû arriver).
  - Ancienneté : bonus de lecture (non stocké, recalculé à l'affichage par `computeDisplayTrustScore`) de +1 point par mois d'ancienneté du compte, plafonné à +24 (2 ans).
  - `TRUST_SCORE_ON_TIME_COMPLETION_POINTS` (paiement/transaction honorée sans litige) est défini mais **pas encore branché** dans les tâches planifiées d'escrow (Phase 3/4) — je n'ai pas voulu modifier ces processors au-delà du strict nécessaire pour la Phase 5. Dites-moi si vous voulez que je l'active (incrément à chaque libération d'escrow normale, sans litige).
- **Types de notifications déclenchant aussi un SMS** (`SMS_WORTHY_TYPES` dans `notifications.service.ts`) : j'ai choisi `DISPUTE_OPENED`, `DISPUTE_RESOLVED` et `WITHDRAWAL_STATUS_CHANGED` — les événements où un utilisateur risque de ne pas consulter l'app à temps et où l'enjeu financier est direct. Les autres types (`GROUP_JOIN_REQUEST`, `GIFT_CARD_SOLD`, etc.) restent in-app uniquement pour limiter les coûts SMS. Dites-moi si la liste doit être étendue ou réduite.
- **Filtrage anti-contournement dans les messages** (`content-filter.util.ts`) : je masque les numéros de téléphone (séquences de ≥7 chiffres) et les liens WhatsApp (`wa.me`, `whatsapp.com`) dans les messages affichés, tout en conservant le texte brut (`Message.originalContent`) pour audit. Je n'ai pas étendu le filtre aux adresses e-mail ni aux autres réseaux sociaux (Telegram, Instagram, etc.) faute d'indication dans le brief. Dites-moi si d'autres canaux de contournement doivent être détectés.
- **Notification de demande d'adhésion à un groupe** : je notifie le propriétaire (`GROUP_JOIN_REQUEST`) uniquement quand la demande reste `PENDING` (approbation manuelle) — pas quand `autoAcceptJoinRequests` est actif, puisque le propriétaire n'a alors rien à approuver. Dites-moi si vous souhaitez quand même l'informer d'une nouvelle adhésion automatique.

## Front-end web — authentification, portefeuille, retraits, profil (Phase 6a, décisions prises)

- **Découpage de la Phase 6 (front-end)** : plutôt que de construire tout `apps/web` en une seule passe, je la découpe en sous-étapes qui suivent l'ordre des phases API déjà construites (confirmé avec vous) : 6a = auth + portefeuille + retraits + profil (cette étape) ; 6b = groupes de partage ; 6c = cartes cadeaux ; 6d = litiges/messagerie/notifications/avis. Le tableau de bord actuel indique explicitement que ces fonctionnalités arrivent plus tard, pour ne jamais laisser de lien mort.
- **Session côté navigateur (BFF plutôt que jetons côté client)** : l'API expose des jetons bearer (`accessToken`/`refreshToken`) dans le corps JSON, pensés pour un client qui les stocke lui-même. J'ai choisi de ne jamais exposer ces jetons au JavaScript du navigateur : `apps/web` les reçoit côté serveur (Route Handlers Next.js) et les garde dans deux cookies `httpOnly` (`pitzaa_access_token`, `pitzaa_refresh_token`). C'est plus sûr contre le XSS, au prix d'un aller-retour supplémentaire par le serveur Next.js pour chaque appel API. Dites-moi si vous préférez une app réellement « SPA » (jetons en mémoire côté client, appels directs du navigateur vers l'API).
- **Formulaires HTML classiques plutôt que Server Actions React** : les mutations (connexion, retrait, mise à jour du profil...) passent par des Route Handlers Next.js (`POST /login/request-otp`, `POST /withdrawals/create`, etc.) déclenchés par de simples `<form method="post">`, plutôt que par des Server Actions `"use server"`. Fonctionne sans JavaScript côté client, et reste testable par de simples requêtes HTTP (ce que j'ai utilisé pour valider le parcours complet avec `curl`, faute d'outil de navigateur dans cet environnement).
- **Rafraîchissement de session dans `proxy.ts`** (le fichier anciennement `middleware.ts`, renommé selon la convention Next.js 16) : à chaque requête, je décode localement (sans vérifier la signature) l'expiration du jeton d'accès pour décider s'il faut appeler `POST /auth/refresh` avant de continuer. Cette vérification locale ne sert qu'à l'expérience utilisateur (éviter un aller-retour API inutile) ; l'API reste la seule autorité qui valide réellement la signature et l'expiration à chaque appel authentifié.
- **Test du parcours complet sans navigateur** : aucun outil de navigateur (Playwright, etc.) n'est disponible dans cet environnement. J'ai validé le parcours réel (inscription/connexion par OTP, tableau de bord, retrait avec OTP, mise à jour du profil/PIN, déconnexion) avec des requêtes `curl` successives contre l'API et la base de données réelles (conteneurs Docker), en nettoyant les données de test ensuite. Les tests automatisés (`apps/web`) couvrent la logique pure (formatage, décodage JWT) et le rendu des pages publiques ; ils ne couvrent pas encore le parcours authentifié de bout en bout (nécessiterait un outil de navigateur ou un framework d'e2e type Playwright/Cypress). Dites-moi si vous souhaitez qu'on ajoute un tel outil pour les prochaines sous-étapes.

## Front-end web — groupes de partage (Phase 6b, décisions prises)

- **`/groups` et `/groups/:id` restent publics (pas de compte requis)** : ça reflète l'API elle-même, où `GET /groups` et `GET /groups/:id` n'exigent aucune authentification et ne filtrent pas par visibilité pour la consultation d'un groupe précis (un groupe `PRIVATE` reste consultable avec le lien direct, seule la liste `/groups` le masque). Seules les pages qui supposent un compte (`/groups/create`, `/groups/mine`) et les actions (rejoindre, payer, gérer) sont protégées.
- **Gestion des membres par le propriétaire affiche des identifiants techniques, pas des noms** : `GET /groups/:id` renvoie les adhésions (`memberships`) sans les informations de profil de l'utilisateur (prénom/téléphone), et il n'existe pas d'endpoint pour consulter le profil public d'un autre utilisateur. En attendant un tel endpoint, le panneau de gestion affiche un identifiant tronqué (`Utilisateur cmxxxxxxxx…`) au lieu d'un nom. Dites-moi si vous voulez que j'ajoute un endpoint minimal (`GET /users/:id/public-profile` par exemple) pour afficher au moins le prénom.
- **Révélation des identifiants partagés : exception au principe « formulaires HTML classiques »** (voir Phase 6a) : un secret déchiffré ne peut pas être renvoyé via une redirection (il apparaîtrait dans l'URL). Cette seule action utilise donc un petit composant client (`"use client"`) qui appelle un Route Handler renvoyant du JSON directement, sans navigation. Toutes les autres mutations du groupe restent de simples formulaires POST.
- **Signalement « pas d'accès » limité au paiement qui vient d'être effectué** : l'API n'expose aucun endpoint pour lister l'historique des paiements d'une adhésion (seul `GET /wallet/me/history` existe, côté grand livre, pas côté `MembershipPayment`). Le lien « Signaler un problème » n'apparaît donc que juste après un paiement réussi (l'id du paiement transite par l'URL de redirection). Un co-abonné ne peut pas encore contester un paiement plus ancien depuis l'interface. Dites-moi si vous voulez un endpoint `GET /memberships/:membershipId/payments` pour lever cette limite.
- **Paiement par mobile money : pas de rafraîchissement automatique** : comme pour les retraits (Phase 6a), un paiement par mobile money revient immédiatement avec un statut `PENDING` (confirmation asynchrone par webhook) ; l'utilisateur doit recharger la page pour voir le statut final. Même limite déjà actée en Phase 6a, pas de changement ici.
- **Prévisualisation du prix sans JavaScript** : plutôt qu'un calcul dynamique côté client, les trois durées possibles (1/3/6 mois) sont précalculées côté serveur avec `computeMembershipPaymentAmount` (le même calcul que l'API) et affichées directement dans les options du menu déroulant.

## Front-end web — cartes cadeaux (Phase 6c, décisions prises)

- **Pas de page de détail par annonce** : l'API n'expose aucun `GET /gift-cards/listings/:id` (seules les listes `listPublic`/`listMine`/`listPendingForAdmin` existent). Plutôt qu'ajouter un nouvel endpoint pour les besoins du front, j'ai conçu l'interface pour s'en passer : la page `/gift-cards` affiche directement une grille de cartes avec un formulaire d'achat intégré à chaque carte (comme une place de marché classique), sans lien profond vers une page dédiée. Dites-moi si vous préférez tout de même un endpoint `GET /gift-cards/listings/:id` et une vraie page de détail (utile par exemple pour partager le lien d'une annonce précise).
- **Aucun parcours KYC pour le vendeur** : il n'existe aucun endpoint de soumission KYC dans l'API (seul le modèle Prisma `KycSubmission` existe, sans contrôleur). Quand un vendeur dépasse le plafond de 300 000 XAF/mois sans être `kycStatus=APPROVED`, l'interface affiche simplement le message d'erreur de l'API avec « contactez le support » — il n'y a nulle part où le rediriger pour réellement faire sa vérification. C'est un vrai manque côté produit, pas quelque chose que le front peut résoudre seul.
- **Vérification du rôle admin côté page, pas dans `proxy.ts`** : `/gift-cards/admin/pending` vérifie `user.role` après avoir récupéré `/auth/me` dans la page elle-même, plutôt que dans le middleware. Le rôle décodé localement depuis le jeton (comme le fait déjà `proxy.ts` pour l'expiration) n'est pas vérifié cryptographiquement ; seule l'autorité de l'API (qui revérifie le rôle à chaque appel et renvoie 403 sinon) protège réellement cette page — la vérification côté page n'est qu'un confort d'affichage.
- **Révélation du code (acheteur et admin) : même exception que le coffre-fort du Phase 6b** — un secret déchiffré ne peut pas transiter par une redirection. Les deux reveal (`/gift-cards/orders/:id/reveal` côté acheteur, `/gift-cards/admin/:id/reveal-code` côté admin) sont de petits composants client qui appellent un Route Handler renvoyant du JSON, affiché sans navigation.

## Front-end web — litiges, messagerie, notifications, avis (Phase 6d, décisions prises)

- **Ajout de `conversation` aux réponses existantes (changement API additif)** : `GET /disputes/mine`, `GET /disputes/admin/pending`, `GET /groups/:id`, `GET /gift-cards/orders/mine` et `GET /gift-cards/listings/mine` ne renvoyaient pas l'id de la conversation associée (le modèle Prisma l'a depuis la Phase 5, mais les `include`/`select` ne la demandaient pas). J'ai ajouté `conversation: true` à ces requêtes pour qu'une seule page de discussion générique (`/messages/:id`) puisse être reliée depuis les groupes, les commandes de cartes cadeaux et les litiges. C'est un ajout de champ non cassant (rien n'est retiré), validé par les tests existants + le parcours réel de bout en bout.
- **Messagerie : une seule page générique `/messages/:id`**, réutilisée partout (groupe, commande, litige) plutôt qu'un fil de discussion dupliqué dans chaque contexte — l'autorisation est déjà vérifiée de façon générique côté API (`assertParticipant`). L'expéditeur n'est affiché que comme « Vous » / « Autre partie » : l'API ne renvoie pas le profil de l'expéditeur avec chaque message (même limite déjà actée en Phase 6b pour la liste des membres d'un groupe).
- **Avis : limités aux transactions dont l'id est déjà connu du front** — pour les cartes cadeaux, l'id de commande est disponible sur `/gift-cards/orders/mine` (acheteur) et `/gift-cards/mine` (vendeur, via `listing.order`), donc le lien « Laisser un avis » y apparaît pour les commandes `ESCROW_RELEASED`/`REFUNDED`. Pour les abonnements partagés, aucun endpoint ne liste l'historique des paiements d'une adhésion (limite déjà notée en Phase 6b) : le lien n'apparaît que juste après un paiement ou une résolution de litige, via l'id transmis dans l'URL de redirection. Un avis plus ancien sur un abonnement ne peut pas encore être laissé depuis l'interface.
- **Avis reçus affichés sur `/profile`** plutôt que sur une page de profil public dédiée (qui n'existe pas encore) : comme `/profile` est déjà la page de l'utilisateur connecté, j'y ai ajouté une section « Avis reçus » alimentée par `GET /reviews/users/:userId` (endpoint public) avec son propre id. Voir un autre utilisateur n'a pas de page dédiée pour l'instant.
- **Pas de badge de notifications non lues dans la navigation** : afficher un compteur dans le menu (app)/layout.tsx aurait ajouté un appel réseau à chaque page authentifiée. Le compteur n'apparaît que sur la page `/notifications` elle-même.
